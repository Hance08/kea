# SPA Ledger Switcher — Design

**Date:** 2026-06-09
**Scope:** SPA-only. No backend changes; the API surface already exists.
**Status:** Approved for planning.

## Problem

Kea supports multiple named SQLite "ledgers" with one marked active at a time. Today the active ledger can only be changed via the CLI (`kea ledger switch <name>`). The SPA:

- gives no UI for switching ledgers,
- displays no indication of which ledger is currently active.

A user who runs `kea ledger switch business` from a terminal sees the browser silently reflect the new ledger's data with no signal that anything changed.

## Goal

Add a ledger switcher to the SPA sidebar so users can see the active ledger at a glance and switch between registered ledgers without leaving the browser.

## Non-goals

- Creating, deleting, or renaming ledgers from the SPA (defer to follow-up PRs).
- A dedicated `useActiveLedger` hook (defer until a second consumer needs the data; YAGNI).
- A first-class "no active ledger" empty state. The SPA currently assumes one ledger is active; this PR maintains that assumption.
- Cross-tab synchronization. `refetchOnWindowFocus` is already disabled app-wide; not addressing here.

## Architecture

One new component owns everything: query, mutation, and dropdown UI.

```
spa/src/components/
  LedgerSwitcher.tsx   (new, ~80 lines)
  Sidebar.tsx          (replace static header with <LedgerSwitcher />)
  ui/
    dropdown-menu.tsx  (generated by shadcn)
    sonner.tsx         (generated by shadcn)
```

The switcher is self-contained — no prop drilling, no provider. `Sidebar.tsx` remains a navigation file.

## Data flow

### Query — list ledgers

```ts
useQuery({ queryKey: ['ledgers'], queryFn: getLedgers })
```

Drives:
- the trigger label (from `data.active`),
- the menu items (`data.items`).

### Mutation — switch ledger

```ts
useMutation({
  mutationFn: (name: string) => switchLedger(name),
  onSuccess: (info) => {
    queryClient.invalidateQueries();          // refetch everything
    toast.success(`Switched to ${info.name}`);
  },
  onError: (err) => {
    toast.error(err instanceof Error ? err.message : 'Switch failed');
  },
});
```

- Global `invalidateQueries()` is intentional: every panel must re-fetch against the new ledger's data. The `['server-config']` query has `staleTime: Infinity`, so invalidating it is safe — it will refetch once and `useServerConfig` consumers will not re-render mid-flight.
- No optimistic update. The server response is the source of truth, and we want the post-switch invalidation to be the unambiguous signal.

## UI states

### Trigger (sidebar header)

| Query state | Render |
| --- | --- |
| Pending | `<Skeleton className="h-5 w-20" />` in the trigger position. |
| Error | Plain `"kea"` text, non-interactive. Silent — other panels will already be surfacing errors. |
| Success | `<DropdownMenuTrigger>` showing `data.active` with a chevron icon. |
| Mutation in-flight | Trigger button rendered but `disabled`. |

### Menu items

| Item | Behavior |
| --- | --- |
| Active ledger | Row shows a check-mark, is `disabled`, no click handler. |
| Other ledgers | Clickable. On select, call `mutation.mutate(name)`. |
| Any row while mutation pending | `disabled`. Spinner replaces the check-mark slot on the row being switched *to*. |

### Single-ledger case

If the registry has only one ledger, the dropdown renders normally with one item — the active row, disabled, with a check-mark. No special-casing. This matches what the user will see after they add a second ledger.

## API additions

### `spa/src/lib/types.ts`

```ts
export interface LedgerInfo {
  name: string;
  path: string;
  active: boolean;
}

export interface LedgerListResponse {
  active: string;
  items: LedgerInfo[];
}
```

### `spa/src/lib/api.ts`

```ts
export function getLedgers(): Promise<LedgerListResponse> {
  return apiFetch<LedgerListResponse>('/api/ledgers');
}

export function switchLedger(name: string): Promise<LedgerInfo> {
  return apiFetch<LedgerInfo>('/api/ledgers/switch', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ name }),
  });
}
```

The existing `apiFetch` already throws `ApiError(status, message, field)` on non-2xx, which is what the toast consumes.

## Backend error contract (already implemented)

Verified in `internal/api/errors.go` and `internal/api/ledgers.go`:

| Failure | HTTP | Body |
| --- | --- | --- |
| Empty / invalid name (path separator, control char) | 400 | `{ message: "...", field: "name" }` |
| Unknown ledger name | 404 | `{ message: "ledger not found: \"x\" — run: kea ledger list" }` |
| Internal failure (DB open etc.) | 500 | `{ message: "..." }` |

The toast displays `error.message` verbatim — all three are user-readable as written, so no branching on status is required.

## shadcn primitives

```
cd spa && npx shadcn@latest add dropdown-menu sonner
```

Both land in `spa/src/components/ui/`. `sonner` brings a `<Toaster />` component that must be mounted once.

### `<Toaster />` mount point

`spa/src/main.tsx`, as a sibling to `<ServerConfigProvider>` inside `<QueryClientProvider>`:

```tsx
<QueryClientProvider client={queryClient}>
  <ServerConfigProvider fallback={...}>
    {() => <RouterProvider router={router} />}
  </ServerConfigProvider>
  <Toaster />
</QueryClientProvider>
```

Placing it inside `QueryClientProvider` is not strictly required (Sonner does not consume query context), but keeps all UI under a single root.

## Testing

New file `spa/src/test/ledger-switcher.test.tsx`. URL-aware `fetch` stub via `vi.stubGlobal`, mirroring `balances.test.tsx`. Test cases:

1. **Trigger shows active ledger name** after `/api/ledgers` resolves.
2. **Menu lists all ledgers**; active row is `disabled` and carries the check-mark indicator.
3. **Successful switch**: clicking a non-active row issues `POST /api/ledgers/switch` with the correct `{name}` body, then a success toast appears.
4. **Failed switch**: mocked 400 response produces an error toast displaying the API's `message`.
5. **Pending switch disables siblings**: while the POST is in flight, other menu items are non-interactive.

The existing `balances.test.tsx` continues to pass — the sidebar still renders in the test app, and the new `/api/ledgers` request resolves through the stub or is irrelevant to that test's assertions.
